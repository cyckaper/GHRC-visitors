# 操作流程：一場參訪從頭到尾

這份文件回答兩件事：**每一個步驟與按鈕是為了什麼**，以及**這個流程哪裡還不合理**。
規格看 `CLAUDE.md`，部署看 `DEPLOY.md`。

後台 `visit.healsdesign.org/admin.html`；最上面一個「這一場」是全站共用的選擇，五個分頁都在那一場上做事。

---

## 一、時間軸：一場參訪會經過什麼

| 什麼時候 | 誰 | 做什麼 | 在哪裡 |
|---|---|---|---|
| 收到來信 | 主辦端 | 貼信 → 抽資料 → 查背景 → 排流程 | 後台「訪前」 |
| 參訪前一兩天 | 主辦端 | 挑頁、產 .pptx、寄確認信 | 後台「簡報」＋「訪前」 |
| 當天 | 來賓 | 掃門口 QR → 看今日流程、五間老師卡片、留 email | 來賓專頁 |
| 當天 | 老師／主持人 | 開簡報（捷徑送出動線訊號） | 研究室電腦 |
| 來賓離開後 | 主持人 | 簽名簿、名片、三十秒口述、當天資料 | 後台「收工」 |
| 一兩天內 | 主辦端 | 草擬並寄出感謝信給名單上每一個人 | 後台「訪後信」 |
| 一週內 | 來賓 | 回三個問題（可不具名） | 來賓專頁 `#respond` |
| 之後 | 主辦端 | 一頁摘要、跨場次彙整；資料自動備份到 Drive | 後台「資料」 |

**設計前提**：來賓只做兩件事——掃一次 QR、回三個問題。其他都在主辦端。

## 二、後台：每個步驟與按鈕的目的

### 最上面那一行

| 元件 | 目的 |
|---|---|
| 這一場（下拉） | 全站共用「現在在處理哪一場」。打開後台就停在今天（沒有就最近）那一場 |
| ＋ 新的一場 | 明確表示「接下來要建新的」——填上單位名稱就自動建好 |
| 已存 14:32 | 自動存的回報。**沒有存檔按鈕**，改了欄位一秒多就存 |
| 刪掉這一場 | 建錯就刪。已經有來賓回覆或已寄出感謝信的不給刪（那不是我們的東西）；Drive 備份不動 |
| 登入／登出 | 貼一次 ADMIN_TOKEN 換成這台裝置的憑證，半年不必再貼。共用電腦用完請登出 |

### 訪前

| 步驟／按鈕 | 目的 | 為什麼需要 |
|---|---|---|
| 1. 貼 email／上傳名單檔 → **AI 抽取** | 讀出單位、人名職稱、**隨行名單與 email**、日期時間、目的、興趣 | 手打十幾個人的資料會漏，而漏掉的正好是訪後信寄不到的人 |
| 2. 確認訪客背景（欄位） | AI 讀的一律要人看過才算 | 抽錯不可怕，抽錯又沒人看才可怕 |
| 　網址代碼 | 來賓專頁網址的後半段 | 寄出信或有人回覆之前都還能改，之後固定（印出去的 QR 不能失效） |
| 　參訪名單 | 訪後信的收件人清單就是這一份 | 只留主要窗口，回饋就只剩一個人的意見 |
| 3. **AI 查訪客背景** | 查公開的專業資料，判斷**可能的參訪目的**、可能最想看哪幾間、可以先準備什麼 | 對方通常不會在信裡寫真正想要什麼；先判斷過，簡報與動線才挑得準 |
| 4. **AI 排行程與選頁** | 排出今日流程（印在簡報第 2 頁）與現場動線，並先挑好頁次 | 時間分配是每場都要重做的算術，交給程式 |
| 　今日流程 | 對來賓公告的時間表 | 同時是簡報第 2 頁與來賓專頁的內容來源 |
| 　現場動線 | 來賓幾點走到哪一間（留 0 表示不去） | 也是動線紀錄的底稿：沒有訊號的時段用它推補 |
| 來賓專頁 ＋ QR | 這一場專屬頁面的網址 | QR 印出來或投在簡報最後一頁，來賓自己掃，不必個別傳網址 |
| 下載收工提醒 .ics | 參訪結束時提醒你拍簽名簿、講口述 | 現場忙完就散了，沒有提醒就不會做 |
| **AI 草擬確認信** | 確認日期時間、附上專頁網址 | 順手把專頁交到對方手上 |

### 簡報

| 步驟／按鈕 | 目的 | 為什麼需要 |
|---|---|---|
| 這場不用簡報，只口頭介紹 | 整頁關掉選頁與產檔 | 有些參訪就是坐下來談，不需要投影片 |
| 選用頁次（依區塊勾） | 決定這一場講哪幾頁 | 母簡報 72 頁不可能全講；必選頁（封面、流程、架構、核心宣稱、謝謝）永遠保留 |
| 全選／全不選 | 快速起點 | |
| 儲存選頁 | 把勾的記在這一場上 | **其實不必按**：產檔時會自動存 |
| **產生簡報 .pptx** | 從母簡報挑出這幾頁、改寫第 1–3 頁、換第二語言、加 QR 頁，直接下載 | 母簡報是設計過的成品，只做子集化不重新生成，設計不會掉 |
| 母簡報（上傳／移除） | 站台存一份母簡報，之後產檔不必每次選檔 | 一次性設定；含影片或太大的檔會先在瀏覽器裡瘦身 |

### 收工（來賓離開後四件事）

| 步驟／按鈕 | 目的 | 為什麼需要 |
|---|---|---|
| 動作一 **上傳並讀字**（簽名簿） | 實體本子拍一張存檔，AI 讀成留言 | 簽名簿是唯一不必請人動手的留話管道；原圖永久保留 |
| 動作二 **拍名片** → 加進這場的名單 | 現場拿到的名片變成名單上的人 | 隨行的人拿不到 email 時的正式備案——訪後信才寄得到他 |
| 動作三 **三十秒口述** → 抽取 → 存入回饋 | 主持人講：誰來、最想看哪一間、問了什麼、有無合作意願 | **受訪的是主持人自己**，不錄來賓（對部長級不禮貌，且被錄只會講官話） |
| 動作四 當天資料（PDF／合照／連結） | 放上來賓專頁 | 感謝信只能承諾頁面上真的有的東西，所以先放再寄信 |
| 兩個連結（`#email`／`#respond`） | 現場留信箱／訪後三個回應項目 | 行程走完才產出：訪前給了也沒用 |

### 訪後信

| 步驟／按鈕 | 目的 |
|---|---|
| 寄件者（中心主任／對口老師） | 決定署名 |
| **AI 草擬感謝信** | 附上當天資料、放進三個回應項目的連結 |
| 寄送對象 | 名單上每一個人 ＋ 當天在專頁留信箱的人；逐一勾選 |
| **寄出** | 用中心的 Gmail 一封一封寄（沒設定 Gmail 就給 mailto 自己寄） |

> 三個回應項目：想合作哪幾間（301–305 複選）、希望我們做什麼、**開放建議欄位**（請益語氣、一句話就好、可不具名）。

### 資料

| 步驟／按鈕 | 目的 |
|---|---|
| 歷次參訪（點一列） | 看那一場的摘要、來賓回覆、現場動線 |
| **AI 產一頁摘要** | 把回覆、動線、口述整理成一頁；同時記下哪幾頁被提問、被提到 |
| 立即備份到 Drive | 手動補救（平常自動備份，一場一個資料夾） |
| **AI 彙整**（跨場次） | 把歷次開放建議一起讀過，找出重複出現的問題 |
| 四個 CSV | 年報與諮詢委員會的原始數字 |

## 三、來賓端（`/<visit_id>`）

同一個網址，依日期換樣子：

| 階段 | 看到什麼 | 為什麼 |
|---|---|---|
| 訪前 | 「將參訪」、今日流程、五間老師卡片 | 先知道會看到什麼、誰負責 |
| 當天 | ＋ 留 email、備援按鍵 | 現場才需要；留信箱是為了訪後寄得到他 |
| 訪後 | 「感謝蒞臨」、當天資料、**三個回應項目** | 從感謝信按進來就直接看到要回的問題 |

全頁英文為主、第二語言為輔（預設中文，韓／日團改韓／日文）。

## 四、流程檢討

### 做對的地方（別「修」掉）

- **沒有存檔動作**、網址在用出去之前可以改、建錯就刪 —— 存檔是系統的帳，不是使用者的事
- **跑得久的 AI 一律走背景函式**，前端輪詢到底不叫人再按一次
- **開放建議可不具名，且後端不補回姓名** —— 這條管道能不能收到真話就靠這個
- **不做滿意度評分、不集章、不發問卷、不錄來賓** —— 每一條都有理由（見 CLAUDE.md 否決清單）
- **拍名片**補名單，讓「隨行的人拿不到 email」有正式解法

### 還不合理的地方（依重要性）

**1. 閉環的最後一段沒接上（最重要）**
`slide_performance` 每場都寫（哪幾頁選了、哪幾頁被提問、哪幾頁在回饋中被提到），但**沒有任何地方讀它**——`planVisit()` 的輸入裡沒有歷史資料。所以「功能 4 回饋功能 2」目前只累積不回饋，這是整個專案的核心主張，卻剛好缺這一段。
→ 建議：`plan` 的提示詞帶「同類單位過去選過哪些頁、哪幾頁引發提問」的統計。

**2. 缺一條「這一場到哪一步」的進度線**
五個分頁是時間順序，但畫面上沒有任何地方告訴你這一場做到哪、下一步是什麼。下拉只顯示 `draft／confirmed／done` 三態，太粗。
→ 建議：「這一場」那一行下面一條打勾清單（抽取 ✓ 背景 ✓ 行程 ✓ 簡報 ✓ 確認信 ✓ ／ 簽名簿 名片 口述 當天資料 ／ 感謝信 摘要），每一格可點、點了跳到對應分頁。這是目前最值得加的東西。

**3. 兩封信在兩個地方**
確認信在「訪前」、感謝信在「訪後信」。同樣是寄信給同一群人、同一套機制，卻要記得在哪一頁。
→ 建議：兩封都放「信件」分頁（依階段顯示哪一封該寄），或至少互相連結。

**4. 一次性設定跟每場的事混在一起**
母簡報上傳在「簡報」分頁底部；Drive、Gmail、SIGNAL_KEY 只在 `DEPLOY.md`。
→ 建議：一個「設定」分頁收母簡報、寄件者預設值、Drive 狀態、老師卡片內容。

**5. 動線這條線在後台幾乎不存在**
研究室捷徑與 NFC 網址只能用 `node scripts/make-shortcuts.mjs` 產生——但架構決定裡自己寫過「主辦端不必開終端機」。
→ 建議：後台一個按鈕產出捷徑與 NFC 網址（含 QR），順便顯示這一場收到了哪些訊號。

**6. 一頁摘要沒有人會記得按**
摘要是 Drive 備份與跨場次彙整的來源，但它藏在「資料」分頁，而且沒有任何提示。
→ 建議：感謝信寄出後在畫面上提示「過幾天回來按一次摘要」；或收到第一筆回覆時自動產一版。

**7. 口述提醒只有 .ics，要人自己下載**
CLAUDE.md 寫的是「依議程結束時間推播提醒」，目前沒有推播。
→ 建議：短期就把 .ics 講清楚（現在的 title 已經說明了）；要真的推播得先決定用什麼管道。

**8. 「儲存選頁」按鈕留著會誤導**
產檔已經會自動存，這顆按鈕現在只是「提前存一次」。
→ 建議：選頁跟訪前一樣自動存，然後把按鈕拿掉。

**9. 來賓專頁三種連結沒在一個地方說清楚**
純網址（訪前給、QR 用）、`#email`（當天留信箱）、`#respond`（訪後三個問題）。
→ 建議：「收工」那一區把三個並列，各寫一句「什麼時候用」。

**10. 待確認事項還開著**
訪後信預設寄件者（目前預設中心主任）、開放建議欄位措辭定稿、簽名簿形式、口述音檔保存期限、各老師的學經歷與照片。這些不是程式問題，但每一項都會影響來賓看到的東西。

### 已知但可接受的取捨

- **`/api/respond` 公開**（不驗證身分）：真匿名的前提就是不能綁身分。網址不公開，風險可接受。
- **多人同時編輯同一場**：自動存是「最後寫的贏」。中心同時操作的人不會超過一兩個。
- **`sheets` 後端刪除是整列清空**（不真的刪列），列號才不會跑掉。
